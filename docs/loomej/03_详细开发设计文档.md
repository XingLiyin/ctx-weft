## 1. Spring Bean 装配

### 1.1 LoomeJRuntimeConfig

`LoomeJRuntimeConfig` 是 shell 层的核心装配类，负责构造 `ProviderRegistry` 并创建 `LoomeJRuntime`。

**Bean 依赖关系**：

```
PostgresMemoryProvider    ─┐
PostgresEventStore         ├─► ProviderRegistry ─► LoomeJRuntime
SpringAiMcpCapabilityProvider ─┘   ↑
DatabaseLLMClientResolver      ────┘
DatabaseTemplateResolver   ─────────┘
```

**Provider 注册顺序**（顺序决定 LinkedHashMap 去重中谁覆盖谁）：

| 顺序 | Bean | 注册条件 | 说明 |
|------|------|---------|------|
| 1 | `OpenAICompatibleLLMClient` | 总是 | 从 `application.yml` 读取 base-url/api-key/model |
| 2 | `DatabaseLLMClientResolver` | 总是 | 多账号动态切换（优先级高于默认 LLMClient）|
| 3 | `PostgresMemoryProvider` | 总是 | MyBatis 注入 |
| 4 | `PostgresEventStore` | 总是 | 同时实现 EventStore + SnapshotStore |
| 5 | `DatabaseTemplateResolver` | 总是 | 从 agent_templates 表读取模板 |
| 6 | `BuiltinToolsCapabilityProvider` | `loomej.builtin-tools.enabled=true` | bash_exec / read_file / write_file 等 |
| 7 | `LocalSkillCapabilityProvider` | `loomej.skills.dir` 目录存在 | 本地 skills/ 目录扫描 |
| 8 | `SpringAiMcpCapabilityProvider` | 总是 | 初始可能无工具；McpConnectionManager `@PostConstruct` 后注入 |
| 9 | `ControlCapabilityProvider` | LoomeJRuntime 构造时自动注册 | submit_task / submit_plan 等控制工具 |
| 10 | `SkillExecutorCapabilityProvider` | LoomeJRuntime 构造时自动注册 | skill 执行工具 |
| 11 | `RemoteSkillCapabilityProvider`（每个 source）| SkillSourceManager `@PostConstruct` | 晚于 LoomeJRuntime 构造，走动态注册 |

**EventBus 订阅者注册**（在 `loomeJRuntime` Bean 创建后立即注册）：

```java
runtime.eventBus().subscribe("event-persister", new EventPersister(eventStore));
runtime.eventBus().subscribe("snapshot-writer", new SnapshotWriter(eventStore, eventStore));
```

`SessionRegistry` 在 `createAndStart()` 时为每个 Session 额外注册一个订阅者（SSE 翻译）。

### 1.2 skills 目录解析策略

`resolveSkillsDir()` 按以下优先级解析 `loomej.skills.dir` 配置：

1. 若为绝对路径 → 直接使用
2. 相对于 JVM 工作目录（`System.getProperty("user.dir")`）
3. 相对于 JAR/classes 所在目录（向上最多 5 层查找）

最终若目录不存在，`LocalSkillCapabilityProvider` 不注册，日志打 WARN。**不抛异常，不阻止启动。**

### 1.3 Bean 初始化顺序与竞争关系

```
Spring 容器启动
  │
  ├─ @Bean 阶段
  │    ProviderRegistry 构造完成
  │    LoomeJRuntime 构造完成（此时 skillProviderIndex 只含 LocalSkill）
  │
  └─ @PostConstruct 阶段（顺序不确定）
       ├─ McpConnectionManager.init()
       │    从 DB 加载所有 MCP 连接，创建 McpSyncClient，注入 SpringAiMcpCapabilityProvider
       │
       └─ SkillSourceManager.restoreAll()
            从 DB 加载 skill sources，创建 RemoteSkillMcpConn，
            向 registry.addCapabilityProvider() 添加 RemoteSkillCapabilityProvider
            （因为 capabilityProviders 是 CopyOnWriteArrayList，此操作线程安全）
```

**关键约束**：LoomeJRuntime 的静态 `skillProviderIndex`（构造时快照）不包含 `@PostConstruct` 后注册的远程 provider。为此，`runTaskInternal()` 在每次任务执行时动态重建 `currentSkillIndex`：

```java
Map<String, SkillCapabilityProvider> currentSkillIndex = new HashMap<>();
for (SkillCapabilityProvider sp : registry.skillProviders()) {
    currentSkillIndex.put(sp.getName(), sp);
}
```

`registry.skillProviders()` 过滤 `capabilityProviders` 中所有 `instanceof SkillCapabilityProvider` 的 provider，包含 `@PostConstruct` 后动态添加的。

## 2. LLM 客户端实现

### 2.1 OpenAICompatibleLLMClient

核心实现，支持任何 OpenAI 格式的 Chat Completion API（Qwen/DashScope、DeepSeek、OpenAI 等）。

**关键参数**：

```java
baseUrl         // API 基础地址，自动补 "v1/chat/completions"
apiKey          // Bearer Token
model           // 模型名（如 "qwen-max"）
contextLimit    // 默认 200_000（token）
maxOutputTokens // 默认 8096
timeoutSec      // HTTP 超时，默认 120s
```

**流式调用机制**：

请求携带 `"stream": true`，HTTP 响应体为 SSE 格式（`data: {...}\n\n`）。`OpenAICompatibleLLMClient.complete()` 返回 `Iterator<LLMChunk>`，内部类 `SseStreamIterator` 懒加载：

- 每次 `next()` 调用从 `BufferedReader` 读一行，解析 `data:` 前缀的 JSON
- `[DONE]` 行 → `hasNext()` 返回 false
- 调用方在虚拟线程上逐块消费，可在 `next()` 调用之间插入 CancelToken 检查

**LLMChunk 类型**：

```java
record LLMChunk(
    ChunkKind kind,   // TEXT_DELTA / TOOL_CALL / REASONING_DELTA / USAGE / ERROR
    String text,      // TEXT_DELTA / ERROR 时有效
    String reasoning, // REASONING_DELTA 时有效（思维链）
    ToolCall toolCall,// TOOL_CALL 时有效
    int promptTokens, // USAGE 时有效
    int completionTokens
)
```

**重试策略**：

在 `complete()` 中有 3 次重试，指数退避（500ms, 1000ms）：
- HTTP 非 200 → 读完 error body，等待后重试
- 网络异常（IOException）→ 等待后重试
- `InterruptedException` → 立即返回 error chunk（不重试）
- 3 次全失败 → 返回 `errorChunks("message")` 迭代器（单个 ERROR 类型 chunk）

**工具调用格式**：

OpenAI 格式的 `tool_calls` 数组可能在多个 SSE chunk 中累积（streaming tool_calls 是增量的）。`SseStreamIterator` 内部维护 `Map<Integer, ToolCallBuilder>` 按 index 聚合，在 `[DONE]` 时 flush 成完整 `ToolCall`。

### 2.2 DatabaseLLMClientResolver

支持按 Session 动态切换 LLM 账号。当 `submit()` 传入 `llmAccount` 和 `llmModel` 时，`DatabaseLLMClientResolver.resolve(llmAccount, llmModel)` 从 `llm_accounts` 表查出对应的 base_url/api_key，创建 `OpenAICompatibleLLMClient` 实例。

`runTaskInternal()` 中的优先级：
1. 若任务的 `extra` 中有 `llmAccount` 字段 → 用 `llmClientResolver.resolve()`
2. 否则 → 用 `registry.llmClient()`（默认 client）

## 3. MCP 连接管理

### 3.1 McpConnectionManager

负责 `McpSyncClient` 的生命周期管理，Spring `@Component`。

**内部状态**：

```
liveClients: ConcurrentHashMap<name, McpSyncClient>
```

**启动流程（`@PostConstruct init()`）**：

1. `SELECT * FROM mcp_connections WHERE enabled=true`
2. 对每条记录调用 `startClient(cfg)`
3. 失败时只打 ERROR 日志，不中止启动

**`startClient()` 实现**：

```
STDIO 类型：
  ServerParameters params = ServerParameters.builder(command)
      .args(argsList).env(envMap).build()
  StdioClientTransport transport = new StdioClientTransport(params)
  McpSyncClient client = McpClient.sync(transport).build()
  client.initialize()
  mcpCapabilityProvider.addClient(name, client)

HTTP 类型：
  HttpClientStreamableHttpTransport transport = new HttpClientStreamableHttpTransport(url)
  McpSyncClient client = McpClient.sync(transport)
      .requestTimeout(Duration.ofSeconds(timeout)).build()
  client.initialize()
  mcpCapabilityProvider.addClient(name, client)
```

**关闭流程（`@PreDestroy destroy()`）**：

遍历 `liveClients`，对每个 client 调用 `client.close()`，关闭底层 stdio 进程或 HTTP 连接。

### 3.2 SpringAiMcpCapabilityProvider

持有所有活跃的 `McpSyncClient` 列表（`CopyOnWriteArrayList`）。

**`list(ctx)` 实现**：遍历所有 client，调用 `client.listTools()`，将每个 MCP 工具的 `inputSchema` 转换为 `Capability`，能力 ID 格式为 `"mcp:<clientName>:<toolName>"`。

**`invoke(capabilityId, args, ctx)` 实现**：

解析 `capabilityId` 提取 clientName 和 toolName，定位对应 client，调用 `client.callTool(new McpSchema.CallToolRequest(toolName, args))`。

注意：普通 MCP 工具调用**不注入 `_meta`**，只有 `RemoteSkillMcpConn` 注入 `_meta`（远程 skill 协议需要，普通 MCP 工具不需要）。

## 4. Remote Skill Source 注册与生命周期

### 4.1 SkillSourceManager

管理远程 skill source 的完整生命周期，Spring `@Component`。

**注册新 source（`registerRemoteMcp()`）**：

1. 检查 `source_name` 唯一性（重复则抛异常）
2. 构造 `SkillSourceEntity`，`INSERT INTO skill_sources`
3. 调用 `createAndRegisterRemote(entity)`:
   - 创建 `RemoteSkillMcpConn`（STDIO 或 HTTP 模式）
   - 调用 `conn.start()`（启动 MCP 子进程或建立 HTTP 连接）
   - 创建 `RemoteSkillCapabilityProvider(sourceName, conn)`
   - `registry.addCapabilityProvider(provider)`（动态注册，线程安全）
   - 记录到 `activeRemote` 和 `remoteConns` Map

**注销（`deregister()`）**：

1. `registry.removeCapabilityProvider("remote_skill_" + sourceName)`
2. 从 `activeRemote`/`remoteConns` Map 移除
3. `conn.stop()`（关闭 MCP 连接）
4. `DELETE FROM skill_sources WHERE source_name=?`

**启动恢复（`@PostConstruct restoreAll()`）**：

从 `skill_sources` 表加载所有 `enabled=true` 的记录，逐一调用 `createAndRegisterRemote()`，失败时打 WARN 继续下一条。

### 4.2 RemoteSkillMcpConn

管理与单个远程 skill MCP server 的连接。

**`_meta` 注入的完整链路**：

```
ActStep / ReasonStep
  → CapabilityGateway.invoke(capId, args, ctx)
      → RemoteSkillCapabilityProvider.loadDefinition(skillName, ctx)
          → RemoteSkillMcpConn.loadSkillMd(skillName, ctx)
              → callTool("loadSkillMd", {skillName}, ctx)
                  → buildMeta(ctx)  生成 _meta Map
                  → McpSchema.CallToolRequest(toolName, args, meta)  三参数构造
                  → conn.callTool(request)  发给 MCP server
```

`buildMeta(ctx)` 实现：

```java
private static Map<String, Object> buildMeta(ProviderContext ctx) {
    if (ctx == null) return Map.of();
    Map<String, Object> meta = new LinkedHashMap<>();
    meta.put("netcowork/sessionId", ctx.sessionId() != null ? ctx.sessionId() : "");
    meta.put("netcowork/agentId",   ctx.agentId()   != null ? ctx.agentId()   : "");
    meta.put("netcowork/taskId",    ctx.taskId()     != null ? ctx.taskId()    : "");
    return meta;
}
```

**`listSkills()` 的 JSON 解析**：

MCP server 通过 TextContent 返回 JSON 字符串（而非 Java List 对象）。正确解析方式：

```java
String text = callToolText("listSkills", Map.of(), ctx);
return objectMapper.readValue(text, new TypeReference<List<Map<String, Object>>>() {});
```

**错误**（已修复）：原来用 `instanceof List<?>` 判断 callTool() 返回值，因为返回类型是 String，永远为 false，导致始终返回空列表。

## 5. HITL 阻塞机制

### 5.1 HitlManager 实现

HITL（Human-In-The-Loop）通过 `CompletableFuture` 实现虚拟线程阻塞等待。

**关键数据结构**：

```java
approvals: ConcurrentHashMap<approvalId, HitlApproval>  // 当前等待的审批
futures:   ConcurrentHashMap<approvalId, CompletableFuture<HitlApproval>>
timeoutSeconds: long  // 默认 300s（5分钟）
```

**`request()` 流程**：

1. 生成 `approvalId`
2. 创建 `CompletableFuture<HitlApproval>`，写入 `futures`
3. emit `HitlRequired` 事件（含 approvalId，SSE 翻译器推 `waiting_input` 给前端）
4. `future.get(timeoutSeconds, SECONDS)` — **阻塞当前虚拟线程**
5. 超时 → 返回 `status=TIMEOUT` 的 approval（不抛异常，让上层决定如何处理）

**`approve()/reject()` 流程**（由 HitlController 调用）：

```java
void resolve(approvalId, status, modifiedArguments) {
    HitlApproval approval = approvals.get(approvalId);
    approval.setStatus(status);
    approval.setModifiedArguments(modifiedArguments);
    approvals.put(approvalId, approval);
    futures.remove(approvalId).complete(approval);  // 解除阻塞
    emit(HitlApproved / HitlRejected / HitlModified 事件)
}
```

**Session 注册/注销**：

`ControlCapabilityProvider.registerSession(sessionId, taskManager, session)` 在 Session 创建时调用，`deregisterSession(sessionId)` 在 Session 完成时调用。这让 `request_human_input` 控制工具能通过 `HitlManager` 向对应 Session 的 context 发起审批请求。

### 5.2 HITL 与 Session 状态的关系

```
HITL 触发（request_human_input 被 LLM 调用）
  → HitlManager.request() 阻塞 ActStep 虚拟线程
  → emit HitlRequired
  → SseEventTranslator 设 entry.status = "PAUSED_HITL"
  → 推 waiting_input 事件给前端

用户操作（POST /hitl/{approvalId}/approve）
  → HitlController.approve()
  → HitlManager.approve(approvalId)
  → CompletableFuture.complete() 解除阻塞
  → ActStep 继续执行
  → emit HitlApproved
  → SseEventTranslator 设 entry.status = "RUNNING"
  → 推 session_update 事件给前端
```

## 6. 数据库表结构与关键 SQL

### 6.1 sessions 表

```sql
CREATE TABLE sessions (
    id              VARCHAR(64)   PRIMARY KEY,
    tenant_id       VARCHAR(64)   NOT NULL DEFAULT 'default',
    status          VARCHAR(32)   NOT NULL DEFAULT 'RUNNING',
    -- status 枚举：RUNNING / PAUSED_HITL / INTERRUPTED / SUCCEEDED / FAILED / CANCELED
    goal            TEXT,                    -- MetadataFiller 异步写入
    user_prompt     TEXT,
    template_id     VARCHAR(128),
    root_agent_id   VARCHAR(64),             -- 用于恢复时重建 memory scope
    token_budget    INTEGER,                 -- 0 = 不限制
    input_tokens    INTEGER       DEFAULT 0,
    output_tokens   INTEGER       DEFAULT 0,
    context_tokens  INTEGER       DEFAULT 0,
    failure_counter INTEGER       DEFAULT 0,
    llm_provider    VARCHAR(128),            -- 对应 llm_accounts.account_name
    llm_model       VARCHAR(128),
    created_at      TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ   NOT NULL DEFAULT NOW()
);
```

### 6.2 tasks 表

```sql
CREATE TABLE tasks (
    id                      VARCHAR(64)   PRIMARY KEY,

    parent_task_id          VARCHAR(64),

    -- kind: REASONING / COMPACT / METADATA_FILLER
    status                  VARCHAR(32)   NOT NULL DEFAULT 'PENDING',

    description             TEXT,

    skill_name              VARCHAR(128),
    creator_agent_id        VARCHAR(64),
    assigned_agent_id       VARCHAR(64),
    share_scope             BOOLEAN       DEFAULT FALSE,
    compact_scope_agent_id  VARCHAR(64),   -- COMPACT 任务专用
    retry_count             INTEGER       DEFAULT 0,

CREATE INDEX idx_tasks_session_id ON tasks(session_id);
```

### 6.3 memory_records 表

```sql
CREATE TABLE memory_records (
    id          VARCHAR(64)   PRIMARY KEY,
    session_id  VARCHAR(64)   NOT NULL,
    task_id     VARCHAR(64),
    agent_id    VARCHAR(64),
    event_type  VARCHAR(64)   NOT NULL,
    -- event_type: USER_PROMPT / LLM_RESPONSE / OBSERVER_SUMMARY / COMPACT_SUMMARY /
    --             TOOL_INVOCATION / TOOL_RESULT / BLACKBOARD_PUBLISH
    role        VARCHAR(32),               -- user / assistant / tool / system
    content     TEXT          NOT NULL,
    topic       VARCHAR(128),             -- BLACKBOARD_PUBLISH 专用
    sequence    BIGINT        NOT NULL,   -- 全局递增，排序基准
    superseded  BOOLEAN       NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_memory_session_task ON memory_records(session_id, task_id);
CREATE INDEX idx_memory_event_type   ON memory_records(event_type);
CREATE INDEX idx_memory_superseded   ON memory_records(session_id, superseded);
```

**关键查询**：

```sql
-- recallRecent：取最新 N 条未 superseded 的指定类型记录
SELECT * FROM memory_records
WHERE session_id = #{sessionId}
  AND (#{taskId}  IS NULL OR task_id  = #{taskId})
  AND (#{agentId} IS NULL OR agent_id = #{agentId})
  AND event_type IN <foreach collection="types" item="t">#{t}</foreach>
  AND superseded = false
ORDER BY sequence DESC
LIMIT #{limit}

-- countRecent：高效计数，不加载 content
SELECT COUNT(*) FROM memory_records
WHERE session_id = #{sessionId}
  AND (#{taskId}  IS NULL OR task_id  = #{taskId})
  AND (#{agentId} IS NULL OR agent_id = #{agentId})
  AND event_type IN (...)
  AND superseded = false

-- applyCompact：标记旧记录为 superseded（保留最近 keepLast 条）
UPDATE memory_records SET superseded = true
WHERE session_id = #{sessionId}
  AND task_id    = #{taskId}
  AND agent_id   = #{agentId}
  AND superseded = false
  AND id NOT IN (
      SELECT id FROM memory_records
      WHERE session_id = #{sessionId}
        AND task_id    = #{taskId}
        AND agent_id   = #{agentId}
        AND superseded = false
      ORDER BY sequence DESC
      LIMIT #{keepLast}
  )
```

**不持久化的事件**：`LLMTokenStreamed`、`LLMReasoningStreamed`（高频流式，无恢复价值）。

**EventPersister 过滤实现**：

```java
private static final Set<String> SKIP = Set.of(
    EventTypes.LLM_TOKEN_STREAMED,
    EventTypes.LLM_REASONING_STREAMED
);

public void onEvent(Event ev) {
    if (!SKIP.contains(ev.type())) {
        eventStore.persist(ev);
    }
}
```

## 7. SessionRegistry 与 SessionEntry

### 7.1 SessionEntry 完整字段

```java
class SessionEntry {
    String sessionId;
    String status;                         // Session 在 SSE 协议层的状态字符串
    boolean sseFinished;                   // true = Session 已结束，新连接立即推 done
    CopyOnWriteArrayList<String> sseBuffer; // SSE JSON 字符串缓冲（全量，连接可从任意位置读）
    StringBuilder streamingTextBuf;        // LLM token 流聚合（synchronized 访问）
    ConcurrentHashMap<String, Map> pendingInvocations; // 等待结果的工具调用（invId → {toolName, args}）
    ConcurrentHashMap<String, Map> tasks;  // taskId → TaskDict（SSE task_updated 用）
    int inputTokens;                       // 累计
    int outputTokens;
    int contextTokens;                     // 最近一次 prompt_tokens
    String updatedAt;
}
```

### 7.2 SSE 推流实现

`GET /sessions/{id}/stream` 端点：

1. 若 `entry.sseFinished=true` → 立即推一条 `done` 事件，关闭连接
2. 创建 `SseEmitter`（无超时或 Long.MAX_VALUE 超时）
3. 设置 `lastIndex = sseBuffer.size()`（只推新消息，不回放历史）
4. 在虚拟线程上循环：`while (!entry.sseFinished) { 等待新消息信号; 推 sseBuffer[lastIndex..]; }`
5. 前端断开重连时，重新走步骤 3，从 sseBuffer 末尾继续（不回放历史）

**`sseBuffer` 的 `done` 事件保留**：Session 完成后 `done` 事件写入 sseBuffer，`sseFinished=true`。下次连接在步骤 1 处被立即推送 `done` 然后关闭，避免前端轮询。

### 7.3 应用重启恢复

`SessionRegistry.loadSessionsFromDb()`（`@PostConstruct`）：

```java
List<SessionEntity> active = sessionMapper.findByStatusIn(
    List.of("RUNNING", "PAUSED_HITL"));

for (SessionEntity row : active) {
    // 1. 将 DB 状态改为 INTERRUPTED
    sessionMapper.updateStatus(row.getId(), "INTERRUPTED");

    // 2. 在内存中重建 SessionEntry（不重建 TaskManager，等用户点恢复）
    SessionEntry entry = new SessionEntry(row.getId());
    entry.status = "INTERRUPTED";
    entries.put(row.getId(), entry);
}
```

用户点"恢复"后，`SessionController.resumeSession()` 调用 `LoomeJRuntime.resumeSession()`，从 DB 加载 tasks 快照重建 TaskManager，重新提交未完成任务到虚拟线程执行。

### 9.2 新增 ContextSource（Prompt 注入）

`ContextSource` 的职责是把 Provider 数据转换为 `ContextBlock`，注入 Prompt 组装流水线。

```java
public class MyContextSource implements ContextSource {

    @Override
    public List<ContextBlock> fetch(ContextRequest req, LoopContext ctx) {
        if (!"act".equals(req.purpose())) return List.of();  // 只在 act 阶段注入

        String data = fetchMyData(req.task(), ctx.providerCtx());
        if (data == null || data.isBlank()) return List.of();

        return List.of(new ContextBlock(
            IdGenerator.block(),
            "my_source",
            ContextBlock.Kind.REFERENCE,  // kind: identity/capabilities/history/blackboard/reference/...
            ContextBlock.Target.MESSAGES, // 注入到 messages 段（而非 system）
            data,
            3,                            // priority（0最高，数字越大越先被裁剪）
            data.length() / 4             // token 估算
        ));
    }
}
```

在 `LoomeJRuntime` 构造时的 `sources` 列表中添加，或修改 `LoomeJRuntime` 构造函数直接插入。

## 10. 常见问题排查

### 远程 skill 返回"未找到对应的任务"

**原因**：MCP 调用缺少 `_meta`，服务端无法根据 `taskId` 找到任务上下文。

**排查**：在 `RemoteSkillMcpConn.callTool()` 打断点，检查 `meta` Map 是否包含非空的 `netcowork/taskId`。若 taskId 为空，检查 `ProviderContext` 的传递链路（LoopContext → RemoteSkillCapabilityProvider → RemoteSkillMcpConn）。

### 远程 skill 在 Available Skills 中不显示

**原因**：`currentSkillIndex` 中没有对应 provider，或 provider 的 `listSkills()` 返回空列表。

**排查步骤**：
1. 在 `LoomeJRuntime.runTaskInternal()` 中 `currentSkillIndex` 构建完毕后打断点，检查 Map 是否包含 `"remote_skill_<sourceName>"` 键
2. 若不包含 → 检查 `registry.skillProviders()` 返回值，确认 `SkillSourceManager.restoreAll()` 是否成功执行
3. 若包含但值为 null 或 list 为空 → 在 `RemoteSkillMcpConn.listSkills()` 打断点，检查 MCP 连接状态和 JSON 解析

### MCP 工具不显示

**排查**：
- `GET /api/v1/mcp/servers` 确认 server 状态
- `McpConnectionManager.liveClients` 是否包含该 server
- `SpringAiMcpCapabilityProvider.list()` 遍历所有 client 调用 `listTools()`，检查返回结果

### Session 卡在 INTERRUPTED

**原因**：进程崩溃导致，INTERRUPTED 表示可恢复状态（非 bug）。

**操作**：`POST /sessions/{id}/resume` 触发恢复流程。

### token_budget 检查位置

在 `ReasonStep.execute()` 入口处：

```java
int tokenBudget = state.session.tokenBudget();
if (tokenBudget > 0 && state.session.tokenUsed() > tokenBudget) {
    throw new RuntimeException("Session token budget exceeded");
}
```

`tokenUsed` 在每次 `LLMResponseFinished` 事件时由 `SseEventTranslator` 累加（`entry.inputTokens + entry.outputTokens`），并通过 `sessionMapper.updateTokens()` 持久化到 DB。

### Compact 没有触发

**排查**：

```java
// ReasonStep 中的触发判断
boolean tokenRatioTriggered = contextLimit > 0 &&
    (double) estimatedTokens / contextLimit >= loopConfig.compactTokenRatio();
boolean messageDeltaTriggered = newMessageDelta >= loopConfig.compactMessageDelta();
```

- 检查 `loopGuard.contextLimit()`：若为 0，token 比例判断不触发
- 检查 `loopGuard.contextTokens()`：若为 0（无 LLM 基线），`estimatedTokens` 为 0，比例判断不触发
- 只有 ActStep 调用过 LLM 后 `loopGuard` 才有基线。新 Session 第一个任务通常不触发
