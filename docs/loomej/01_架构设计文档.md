## 1. 系统定位与设计原则

LoomeJ 是 Java 21 实现的 Agent 执行框架，目标是把"用户发起一段对话 → Agent 自主规划与执行多轮工具调用 → 完成任务"这个流程做成可控、可观察、可恢复的生产服务。

**核心矛盾**：LLM 执行是长时阻塞操作（几秒到几分钟），同时需要实时流推送、支持中断恢复、支持多任务并行。传统线程模型下这三点互相掣肘。

**设计原则**：

| 原则 | 体现方式 |
|------|---------|
| **Step 化**：Agent 循环不是黑盒，每个最小执行单元可单独观察 | StepDriver 逐步驱动，每步边界 emit 事件 |
| **协议优先**：框架不绑定具体 LLM/存储/技能实现 | 所有外部依赖通过 Protocol 接口注入 |
| **事件溯源**：状态不直接持久化，所有变更以事件表达 | EventStore 持久化事件，Reducers 重建状态 |
| **Streaming First**：前端感知每个 LLM token、每个工具调用 | 内核事件直接映射 SSE，零延迟转发 |
| **协作式取消**：中断不强杀线程，逐层传递 CancelToken | CancelToken.raiseIfCancelled() 在步骤边界调用 |
| **虚拟线程友好**：每个任务一根虚拟线程，可自由阻塞 IO | Java 21 Project Loom |

## 2. 模块划分

项目由两个 Maven 模块组成：

```
loomej/
├── loomej-core/          纯 Java，不依赖 Spring
│   ├── assembler/        Prompt 组装（ContextAssembler + 各 Source）
│   ├── auth/             Authorizer 接口 + AllowAllAuthorizer 默认实现
│   ├── control/          事件重放/快照（Reducers、RunStateView、Converters）
│   ├── events/           事件类型（EventTypes）、EventBus、Event 记录
│   ├── llm/              LLMClient 接口 + OpenAICompatibleLLMClient
│   ├── loop/             StepDriver、LoopContext（record）、LoopState、TurnRecord、Verdict、Step 接口
│   │   └── steps/        ReasonStep、ActStep、ObserveStep、FinalizeStep、
│   │                      CompactStep、SuspendStep、MetadataFillerStep
│   ├── orchestrator/     ProviderRegistry、TaskManager、CapabilityCache、
│   │                      HitlManager、ControlCapabilityProvider、
│   │                      SkillExecutorCapabilityProvider、CancelToken
│   ├── protocols/        所有协议接口（见第 4 节）
│   ├── runtime/          LoomeJRuntime（顶层协调器）+ RunHandle
│   ├── state/            Session、Task、Agent、LoopGuard 等领域对象
│   └── util/             IdGenerator、TokenEstimator
│
└── loomej-shell/         Spring Boot，依赖 loomej-core
    ├── config/           LoomeJRuntimeConfig（Spring Bean 装配）
    ├── session/          SessionController、SessionRegistry、SessionEntry、
    │                      SseEventTranslator
    ├── task/             TaskEntity、TaskMapper（MyBatis）
    ├── memory/           PostgresMemoryProvider
    ├── eventstore/       PostgresEventStore（实现 EventStore + SnapshotStore）
    ├── llm/              DatabaseLLMClientResolver
    ├── template/         DatabaseTemplateResolver
    ├── mcp/              SpringAiMcpCapabilityProvider、McpConnectionManager
    ├── skillsource/      RemoteSkillCapabilityProvider、RemoteSkillMcpConn、
    │                      SkillSourceManager
    └── hitl/             HitlController
```

**模块边界规则**：
- `loomej-core` 不知道 Spring、PostgreSQL、MCP，也不知道具体 LLM API 格式
- `loomej-shell` 实现 core 定义的所有 Protocol 接口，通过 `ProviderRegistry` 注入
- core 与 shell 的唯一耦合点是 `ProviderRegistry` 和 `BiConsumer<String,String> rootAgentIdPersister`（用于异步持久化 rootAgentId，避免 core 直接依赖 shell 数据层）

## 3. 核心领域模型

### 3.1 Session（会话）

代表用户与系统的一次完整对话生命周期。一个 Session 包含一棵 Task 树。

```
Session
  id:            String          全局唯一，格式 "sess_<nanoid>"
  tenantId:      String          多租户隔离（默认 "default"）
  status:        SessionStatus   见状态机
  goal:          String          由 MetadataFiller 异步填写的摘要目标
  userPrompt:    String          用户原始输入
  templateId:    String          使用的 Agent 模板 ID
  rootAgentId:   String          根任务的 Agent ID（内存 scope 的锚点）
  llmProvider:   String          LLM 账号标识（对应 llm_accounts.account_name）
  llmModel:      String          具体模型名（覆盖账号默认值）
  tokenBudget:   int             Session 级 token 总预算（0=不限制）
  tokenUsed:     int             已消耗 token 总量（inputTokens + outputTokens）
```

**Session 状态机**：

```
            ┌───────────────────────────────────────────┐
   创建      │                                           │
   ──────►  RUNNING ──── 用户中断/cancelToken ────►  INTERRUPTED
             │                                      （可恢复，显示恢复按钮）
             │
             ├── 所有 Task 成功 ──────────────────► SUCCEEDED
             │
             ├── 失败计数超阈值 ─────────────────► FAILED
             │
             ├── runtime.interruptSession() ──────► CANCELED
             │   （CancelledException 路径）         （终态，无恢复按钮）
             │
             └── 等待 HITL ──────────────────────► PAUSED_HITL
                                                    │
                                                    └── HITL 完成 ──► RUNNING
```

**INTERRUPTED vs CANCELED 的区别**：
- `INTERRUPTED`：进程崩溃或服务重启导致的非预期中断，对应 Session 原本在运行、进程意外退出后标记；用户可以点"恢复"继续
- `CANCELED`：用户主动调用 `POST /sessions/{id}/interrupt`，`CancelToken` 被触发，`CancelledException` 被捕获后 Session 进入 `CANCELED`；这是终态，不可恢复

### 3.2 Task（任务）

Agent 执行的工作单元。Session 下形成 DAG（通常是树，支持兄弟依赖）。

```
Task
  id:                String
  sessionId:         String
  parentTaskId:      String          null 表示根任务
  dagDeps:           List<String>    前置任务 ID 列表（DAG 依赖，非树边）
  kind:              TaskKind        REASONING / COMPACT / METADATA_FILLER
  status:            TaskStatus      见状态机
  title:             String          任务标题
  description:       String          详细描述
  userPrompt:        String          传给 Agent 的用户消息
  userPromptInMemory: boolean        USER_PROMPT 已写入 memory，防重复写
  settings:          TaskSettings    密封类，三种子类型
  assignedAgentId:   String          运行此任务的 Agent ID
  creatorAgentId:    String          创建此任务的 Agent ID
  processReport:     String          ObserveStep 写的任务总结（父任务重新激活后可读）
  actorDone:         boolean         ActStep 是否正常完成（Observe 阶段用）
  retryCount:        int             当前重试次数
  maxRetries:        int             最大重试次数
```

**TaskSettings（密封类）**：

| 子类型 | 字段 | 用途 |
|--------|------|------|
| `Normal` | skillName, useSubagent, templateId, inheritMemory, dagDeps, purpose, extra | 普通推理任务 |
| `Compact` | templateId, compactScopeAgentId | 内存压缩任务（由 ReasonStep 自动派生） |
| `MetadataFiller` | — | 后台填写 Session.goal 的守护任务 |

**Task 状态机**：

```
  PENDING ──── TaskManager.drain() ────► ACTIVE（AgentLoop 运行中）
     ▲                │
     │                ├── 调用 submit_task/submit_plan ──► SUSPENDED（等子任务）
     │                │         子任务全部完成后          ──► PENDING（重新排队）
     │                │
     │                ├── ObserveStep verdict=success ────► FINISHED
     │                │
     │                ├── ObserveStep verdict=failed  ────► FAILED（可重试则回 PENDING）
     │                │
     │                └── CancelToken 触发 ─────────────► CANCELED
     └── 重试 ────────────────────────────────────────────┘
```

### 3.3 Agent（代理）

附属于 Task 的执行者，持有所有运行时配置与测量值。每个 Task 在启动时实例化一个 Agent。

```
Agent
  id:                 String          格式 "agent_<nanoid>"
  sessionId:          String
  tenantId:           String
  model:              String          LLM 模型名
  templateId:         String          绑定的 Agent 模板
  templateVersion:    String
  status:             String          "RUNNING" / "FINISHED" / "FAILED"
  parentAgentId:      String          父任务的 Agent（用于 spawnDepth 计算）
  spawnDepth:         int             嵌套深度（根=0）；超过 LoopConfig.maxSpawnDepth 禁止继续派生
  boundCapabilityIds: List<String>    本次 ReasonStep 绑定的能力 ID 列表
  loopGuard:          LoopGuard       运行时测量值（可变）
  loopConfig:         LoopConfig      循环参数（不可变，来自模板）
  memoryConfig:       MemoryConfig    记忆配置
  runtime:            Map<String,Object>  扩展字段
```

**LoopGuard（运行时测量）**：

```
LoopGuard
  turnsUsed:              int    LLM 调用累计次数（跨 Task）
  contextTokens:          int    上次 LLM 调用返回的 prompt_tokens（基线）；0 = 无基线
  contextMessageCount:    int    基线时刻的消息总数
  contextLimit:           int    LLM 上下文硬上限（从 LLM 响应中更新）
  lastCompactAtMessage:   int    上次 Compact 时的消息数（用于 messageDelta 触发判断）
```

**LoopConfig（模板级不可变配置）**：

```
LoopConfig
  maxTurnsPerAct:        int     ActStep 内最多 LLM 调用轮次（默认 10）
  maxTurnsPerObserve:    int     ObserveStep 内最多轮次（默认 5）
  compactTokenRatio:     double  token/limit 达到此比例触发 Compact（默认 0.7）
  compactMessageDelta:   int     自上次 Compact 后新增消息数超此值触发（默认 20）
  compactKeepLast:       int     Compact 后保留最近 N 条消息（默认 6）
  maxSpawnDepth:         int     最大 Agent 嵌套深度（默认 3）
  skillInstructionLimit: int     技能 body 注入字符数上限（默认 8000）
```

**MemoryConfig（记忆配置）**：

```
MemoryConfig
  shortMemoryLimit:      int     recallRecent 默认返回条数（默认 20）
  semanticRecallTopK:    int     语义搜索返回 top-K（默认 5）
  longMemoryExpireDays:  int     长期记忆过期天数（默认 30）
```

## 4. 协议层：Provider 体系

所有外部依赖均定义为 Java 接口（Protocol），放在 `loomej-core/protocols/` 包。loomej-shell 提供生产实现，测试可以提供 Mock 实现。

### 4.1 ProviderRegistry

`ProviderRegistry` 是 core 层的依赖注入容器，所有 Provider 通过它传递给运行时。

```
ProviderRegistry
  llmClient:              LLMClient                    （必填）
  llmClientResolver:      LLMClientResolver            （可选，多账号切换）
  memoryProvider:         MemoryProvider               （必填）
  templateResolver:       TemplateResolver             （可选）
  authorizer:             Authorizer                   （可选，默认 AllowAllAuthorizer）
  eventStore:             EventStore                   （可选，无则不持久化事件）
  snapshotStore:          SnapshotStore                （可选）
  capabilityProviders:    CopyOnWriteArrayList<CapabilityProvider>
  knowledgeProviders:     CopyOnWriteArrayList<KnowledgeProvider>
```

**为什么用 `CopyOnWriteArrayList`**：SkillSourceManager 在 `@PostConstruct` 中向 registry 动态添加 RemoteSkillCapabilityProvider，此时 LoomeJRuntime 已经构造完毕并可能已经在处理请求。用 `CopyOnWriteArrayList` 保证并发安全，且读者（StepDriver/ReasonStep）无需加锁。

### 4.2 CapabilityProvider 协议体系

能力提供者有三层接口继承关系：

```
CapabilityProvider（基础接口）
  getName()   → String
  list(ctx)   → List<Capability>         列出所有能力
  retrieve(ctx) → List<Capability>       上下文感知子集（默认返回全部）

  ├── ToolCapabilityProvider（可执行工具）
  │     invoke(capabilityId, args, ctx) → Iterator<CapabilityEvent>   （阻塞迭代器）
  │     cancel(invocationId, ctx)                                      （协作取消）
  │
  └── SkillCapabilityProvider（技能提供者）
        loadDefinition(skillName, ctx) → SkillDefinition    （技能 body + frontmatter）
        listFiles(skillName, pattern, limit, ctx) → List<String>
        loadResource(skillName, resourcePath, ctx) → String
        execScript(skillName, scriptPath, args, ctx) → String
```

**为什么 `invoke` 返回 `Iterator` 而非 `Stream` 或 `Future`**：

Iterator 是虚拟线程友好的阻塞迭代器，每次 `next()` 可以安全阻塞——调用方运行在虚拟线程上不会浪费平台线程。如果用 `CompletableFuture` 或 `Stream`，ActStep 需要处理更复杂的组合语义（错误、取消、部分结果）。Iterator 语义最简单，且与 Java for-each 语法天然契合，便于在 `next()` 之间插入 CancelToken 检查点。

**Capability 数据结构**：

```
Capability（接口）
  id()         → String      全局唯一 ID，格式 "<provider>:<name>"（如 "builtin:bash_exec"）
  name()       → String      LLM 看到的工具名（如 "bash_exec"）
  description()→ String
  inputSchema()→ Map<String, Object>    JSON Schema
  kind()       → CapabilityKind         TOOL / SKILL / CONTROL

  └── SkillCapability extends Capability
        providerName()  → String
        skillMd()       → String     技能 body（系统提示片段）
        version()       → String
```

### 4.3 MemoryProvider 协议

```
MemoryProvider
  ingest(event, ctx)  → String                         写入记忆事件，返回 ID
  recallRecent(scope, types, limit, ctx) → List<MemoryRecord>    按序号倒序取最近 N 条
  recallTopic(topic, since, ctx) → TopicRecallResult   黑板订阅拉取
  recallSemantic(query, scope, topK, ctx) → List<MemoryRecord>   语义搜索（不支持则返空列表）
  subscribeTopic(sessionId, topic, intent, ctx) → String         订阅黑板主题
  applyCompact(scope, summary, keepLast, ctx) → CompactResult    执行压缩
  countRecent(scope, types, ctx) → int                           计数（不加载内容）
```

**MemoryScope 的三个维度**：

```
MemoryScope
  sessionId:  String   必填，隔离不同会话
  taskId:     String   可选，进一步隔离到任务级（null = session 级）
  agentId:    String   可选，进一步隔离到 Agent 级
```

多数查询使用 `MemoryScope.task(sessionId, taskId, agentId)`，即"只看当前 Agent 在当前 Task 下写入的记忆"。跨 Task 读取（父子任务结果共享）通过 Blackboard 机制实现，而非直接放宽 scope。

**MemoryEvent 结构**：

```
MemoryEvent
  type:      MemoryEventType      USER_PROMPT / LLM_RESPONSE / OBSERVER_SUMMARY /
                                   COMPACT_SUMMARY / TOOL_INVOCATION / TOOL_RESULT /
                                   BLACKBOARD_PUBLISH
  role:      String               "user" / "assistant" / "tool" / "system"
  content:   String               事件内容
  topic:     String               BLACKBOARD_PUBLISH 专用
  scope:     MemoryScope
  metadata:  Map<String, Object>  附加字段
```

**各类型的作用**：

| 类型 | 谁写 | 参与 recallRecent 默认查询 | 说明 |
|------|------|--------------------------|------|
| `USER_PROMPT` | StepDriver（任务开始前）| 是 | 用户消息，每 Task 写一次 |
| `LLM_RESPONSE` | ActStep 每轮 LLM 响应后 | 是（Compact 计数用）| Actor 的 LLM 输出 |
| `OBSERVER_SUMMARY` | FinalizeStep | 是 | Observer 的任务总结，进入下轮 prompt |
| `COMPACT_SUMMARY` | CompactStep | 是（Compact 计数用）| 压缩后的历史摘要 |
| `TOOL_INVOCATION` | ActStep | 否（存档备用）| 工具调用记录，外部 memory 系统可索引 |
| `TOOL_RESULT` | ActStep | 否（存档备用）| 工具返回结果 |
| `BLACKBOARD_PUBLISH` | FinalizeStep（有 outputs 时）| 否（走 topic 查询）| 跨 Agent 结果共享 |

### 4.4 其他 Provider 接口

**TemplateResolver**：

```
resolveTemplate(templateId, ctx) → AgentTemplate
```

`AgentTemplate` 包含：`identity`（Map<String, IdentityFacet>，按 purpose 索引）、`capabilityRefs`（List<CapabilityRef>）、`loopConfig`、`memoryConfig`。

`IdentityFacet` 有两个 purpose：
- `"act"`：提供给 Actor LLM 的系统提示（人格/能力描述）
- `"observe"`：提供给 Observer LLM 的系统提示（评估职责/判断准则）

**ProviderContext**：

每次调用任何 Provider 方法时都要传入 `ProviderContext`，它携带当前调用的执行上下文，不承载业务语义：

```
ProviderContext（record）
  sessionId:     String
  tenantId:      String
  taskId:        String
  agentId:       String
  traceId:       String
  invocationId:  String    工具调用时由 ActStep 设置
  timestamp:     Instant
  skillName:     String    当前任务分配的技能名
  extra:         Map<String, Object>
```

这个设计让 Provider 能访问到"是谁在什么任务上下文中调用我"，而不需要直接依赖 Task/Agent 领域对象。远程 MCP 工具通过 `_meta` 字段把 `sessionId/agentId/taskId` 传递给服务端（见第 9 节）。

## 5. 运行时骨架：Session / Task 生命周期

### 5.1 LoomeJRuntime 的职责

`LoomeJRuntime` 是 core 层的顶层协调器，由 shell 层的 `LoomeJRuntimeConfig`（Spring Bean）构造并注入到 Spring 容器。它的职责：

1. **Session 生命周期管理**：createSession / resumeSession / recoverSession / interruptSession
2. **Task 分发**：为每个 Session 维护一个 `TaskManager`，任务 ready 时启动虚拟线程运行 `runTask()`
3. **运行时状态维护**：
   - `sessions`：sessionId → Session（内存 Map）
   - `sessionManagers`：sessionId → TaskManager
   - `cancelTokens`：taskId → CancelToken
   - `runningThreads`：taskId → Thread（用于 interrupt 阻塞的 LLM 调用）
   - `taskAgentIds`：taskId → agentId（内存 scope 恢复用）
4. **EventBus 管理**：单一 `InProcessEventBus` 实例，所有订阅者通过它通信
5. **Provider 自动注册**：构造时自动向 registry 添加 `ControlCapabilityProvider` 和 `SkillExecutorCapabilityProvider`

**关于 `skillProviderIndex` 的演化**：

LoomeJRuntime 构造函数中建立的 `skillProviderIndex` 是启动时快照（静态），只包含 `@PostConstruct` 之前注册的 skill provider。但 `SkillSourceManager.restoreAll()` 是 `@PostConstruct`，晚于 LoomeJRuntime 构造完成。

解决方案：`runTaskInternal()` 在每次任务启动时动态构建 `currentSkillIndex`（扫描 `registry.skillProviders()`），覆盖静态快照。因为 `capabilityProviders` 是 `CopyOnWriteArrayList`，`@PostConstruct` 后加进来的远程 skill provider 也会被包含。

### 5.2 SessionRegistry（Shell 层协调器）

`SessionRegistry` 是 shell 层对外的 Session 管理门面，Spring Bean。它的职责：

1. 接受 `SessionController` 的请求，在数据库创建 sessions/tasks 记录
2. 调用 `LoomeJRuntime.createSession()` 创建内存状态
3. 调用 `LoomeJRuntime.submit()` 触发任务执行
4. 订阅 `EventBus`，将 core 事件翻译为 SSE JSON 并写入 `SessionEntry.sseBuffer`
5. 应用重启时调用 `loadSessionsFromDb()`，将 RUNNING 状态的 Session 标记为 INTERRUPTED

### 5.3 TaskManager 的 DAG 调度

每个 Session 有一个 `TaskManager`，管理该 Session 下所有 Task 的执行顺序。

```
TaskManager 内部数据结构：
  tasks:       ConcurrentHashMap<taskId, Task>
  parentMap:   ConcurrentHashMap<childId, parentId>    父子映射
  childrenOf:  ConcurrentHashMap<parentId, Set<childId>> 子集合
  queue:       LinkedBlockingDeque<Task>               待执行队列
  running:     ConcurrentHashSet<taskId>               运行中的任务
  completed:   ConcurrentHashSet<taskId>               已完成任务
  maxConcurrent: int                                   最大并发数（默认 4）
```

**drain() 逻辑**（任务如何从 queue 进入 running）：

1. 从 queue 取出下一个 Task
2. 检查 `running.size() < maxConcurrent`（并发上限）
3. 检查 `dagDeps` 是否全部在 `completed` 中（DAG 前置依赖满足）
4. 检查父任务是否在 `running` 中——若是，则子任务必须等待父任务进入 SUSPENDED 后才能开始（确保父先于子挂起，避免并发修改）
5. 通过所有检查后，在虚拟线程中调用 `runner.accept(sessionId, taskId)`

**父任务恢复（tryResumeParent）**：

当一个任务完成时，TaskManager 检查其父任务的所有子任务是否全部进入 `completed`。若是，则把父任务从 SUSPENDED 状态重新加入队列（变回 PENDING），让 Agent 继续其 ObserveStep。

### 5.4 完整请求流程（创建 Session 到 SSE 推流）


## 6. Agent 循环引擎（Step Loop）

### 6.1 为什么 Step 化

AgentLoop 如果是单一不可中断的方法，中途无法 pause/inspect/cancel，也无法在崩溃后从中间恢复。Step 化的收益：

- 每步完成后 emit 事件，外部观察者（前端、日志）看到细粒度进度
- CancelToken 在步骤边界检查，取消响应时间 ≤ 一步执行时间
- 崩溃恢复从快照记录的 step 重新开始，不需要全量重放

### 6.2 StepDriver

`StepDriver` 持有 `Map<String, Step>` 和初始步骤名，同步驱动步骤链。它的设计要点：

1. 在每步开始前调用 `cancelToken.raiseIfCancelled()`——这是 CancelToken 的唯一"检查点"
2. 每步返回 `StepOutcome`，其中 `nextStep` 字段决定下一步（null = 循环结束）
3. `StepOutcome.statePatch` 是增量更新 Map，通过 `LoopState.applyPatch()` 应用
4. 在第一步开始前，`ingestUserPromptIfNeeded()` 将 Task.userPrompt 写入记忆（USER_PROMPT 类型），格式为：

```
（当 title 和 description 都不为空时）
## Current Task
{title}
{description}

## Current Message
{userPrompt}

（仅有 userPrompt 时）
## Current Message
{userPrompt}
```

### 6.3 Step 接口

```java
interface Step {
    String name();
    StepOutcome execute(LoopState state, LoopContext ctx);
}

record StepOutcome(
    String nextStep,          // null = 结束
    Map<String, Object> statePatch,
    List<Event> events,       // 步骤产生的事件（由 StepDriver 统一 emit）
    boolean requestPause      // 主动暂停（目前未使用）
)
```

### 6.4 LoopContext（依赖容器）

每次任务执行（`runTaskInternal`）构建一个 `LoopContext`，所有 Step 通过它访问依赖：

```java
record LoopContext(
    ContextAssembler assembler,        // Prompt 组装器
    LLMClient llm,                     // LLM 客户端
    MemoryProvider memory,             // 记忆提供者
    EventBus eventBus,                 // 事件总线
    ProviderContext providerCtx,       // 当前任务的执行上下文
    CapabilityCache capabilityCache,   // ReasonStep 绑定的能力缓存（按 agentId）
    List<CapabilityProvider> capabilityProviders, // 当前可用的 Provider 列表（快照）
    CapabilityGateway capabilityGateway,           // 能力调用网关（含 HITL 拦截）
    Authorizer authorizer,             // HITL 授权检查
    Map<String, SkillCapabilityProvider> skillProviderIndex, // 技能 Provider 索引
    CancelToken cancelToken,           // 协作取消令牌
    TemplateResolver templateResolver,
    TaskManager taskManager,           // 派发子任务用
    HitlManager hitlManager            // HITL 管理
)
```

`capabilityProviders` 是 `registry.capabilityProviders()` 返回的快照（`Collections.unmodifiableList` 包装），任务运行期间不会感知后续新增的 provider——如需在任务中看到新 provider，需重新启动任务。

### 6.5 LoopState（可变状态）

每次任务执行持有一个 `LoopState` 实例，单虚拟线程内串行修改（无并发问题）：

```java
class LoopState {
    final String runId;
    final Session session;
    final Task task;
    final Agent agent;
    final MemoryScope scope;
    long sequenceCounter;          // 用于 Event.sequence
    AssembledPrompt assembledPrompt;  // ReasonStep 写，ActStep 读
    List<TurnRecord> transcript;   // ActStep 多轮记录
    Verdict verdict;               // ObserveStep 写，FinalizeStep 读
    String actExitReason;          // ActStep 退出原因
    Map<String, Object> extra;     // 扩展字段（模板对象等）
}
```

### 6.6 默认 Step 链路

**正常路径**（大多数任务）：

```
reason → act → observe → finalize → null（任务结束）
```

**Compact 路径**（记忆累积超限时）：

```
reason → [compact 子任务派生] → null（当前任务 SUSPENDED）
        ↓（子任务独立运行）
compact → null
        ↓（子任务完成，父任务重新激活）
reason → act → observe → finalize → null
```

**子任务路径**（Agent 调用 submit_task/submit_plan）：

```
ActStep 内调用 submit_task
  → Task.status = SUSPENDED
  → 子任务 push 到 TaskManager
  → ActStep 返回 next=null（当前任务挂起）
  
子任务运行完毕后，TaskManager.tryResumeParent() 触发
  → 父任务重新 PENDING
  → 父任务重新进入 reason step
```

**MetadataFiller 路径**（后台守护任务）：

每次新 Session 创建时并行 spawn 一个 MetadataFiller 任务，专门运行 MetadataFillerStep：向 LLM 发一次请求，提取 `goal` 字段写入 Session。它不进入 reason/act/observe 循环，只执行单步，执行完毕后自动结束（不触发 session done callback）。

### 6.7 各 Step 职责详解

#### ReasonStep

职责：token 预算检查 → Compact 触发判断 → 能力绑定 → Prompt 组装

**Compact 触发条件**（两个条件之一满足即触发）：

1. `estimatedTokens / contextLimit >= loopConfig.compactTokenRatio`（默认 0.7）
2. `newMessageDelta >= loopConfig.compactMessageDelta`（默认 20）

其中 `estimatedTokens` 的计算：
- 若 `loopGuard.contextTokens > 0`（有 LLM 精确基线）：基线 + 自基线以来新增记录的字符数/4（粗略估算 token）
- 若无基线：先走正常组装，用 prompt.tokenCount() 作为估算值

触发后 ReasonStep 创建一个 `TaskSettings.Compact` 类型的子任务 push 给 TaskManager，当前任务进入 SUSPENDED，ReasonStep 返回 `StepOutcome.done()`（nextStep=null）。

**能力绑定（resolveCapabilities）**：

使用 `LinkedHashMap<name, Capability>` 去重，遍历顺序 builtin → LocalSkill → MCP，后者覆盖前者，确保 MCP 工具优先级最高（同名情况下 MCP 替换 builtin）。

若任务有 `assignedSkill`，则只保留与之匹配的 SkillCapability（其他 Skill 过滤掉），但 Tool 类 capability 全部保留。

绑定结果写入 `CapabilityCache.put(agentId, boundCaps)`，供 ActStep/ObserveStep 查询（避免每轮重新 resolve）。

**技能指令加载（loadSkillInstructions）**：

与能力绑定分离，ReasonStep 在能力绑定后专门调用一次 `ctx.skillProviderIndex.get(assignedSkill).loadDefinition()`，把 skill body 作为 `skillInstructions` 字段传入 `ContextRequest`，在 ContextAssembler 中注入到系统 Prompt 的 `## Available Skills` 区域。这确保即使 skill 在能力列表中被过滤，系统提示里的技能说明也能正常注入。

#### ActStep

职责：多轮 LLM 推理 + 能力调用，直到无工具调用（正常结束）或达到 max_turns 或任务被 SUSPENDED。

**每轮（turn）内部流程**：

```
1. cancelToken.raiseIfCancelled()（cancel 检查点）
2. 发送 Prompt → LLM（流式）
   - 每个 token chunk → emit LLMTokenStreamed 事件
   - 最终 → emit LLMResponseFinished（含 promptTokens/completionTokens）
3. 更新 LoopGuard 基线：
   loopGuard.updateBaseline(promptTokens, currentMessageCount)
   loopGuard.incrementTurns()
4. 如无 tool_calls → 本步正常结束，nextStep="observe"
5. 如有 tool_calls → 顺序调用每个能力（通过 CapabilityGateway）
   - 每次调用前 cancelToken 检查
   - emit CapabilityInvoked / CapabilityProgress / CapabilityFinished/Failed
   - 若 control capability 返回 task_suspended=true → 退出循环
6. 把 tool_results 追加到 Prompt，进入下一轮
```

**ActStep 结束条件**：

| 结束原因 | actExitReason | nextStep |
|---------|---------------|---------|
| LLM 不再调用工具 | `"normal"` | `"observe"` |
| Control capability 挂起了任务 | `"actor_done"` | `null` |
| 达到 max_turns | `"max_turns"` | `null`（Task FAILED）|
| context 超限 | `"context_limit"` | `null` |
| CancelToken 触发 | — | 抛 CancelledException |

**Memory 摄取契约**：每次 LLM 调用后 ingest `LLM_RESPONSE`，每次工具调用前后 ingest `TOOL_INVOCATION`/`TOOL_RESULT`。这些记录不进入 `recallRecent` 的默认查询（过滤了 LLM_RESPONSE / TOOL_* 类型），但外部 Memory 实现（如 Mem0）可以订阅这些事件建立语义索引。

#### ObserveStep

职责：评估 actor 执行结果，产出 `Verdict`（task_outcome + summary）。

ObserveStep 使用 purpose=`"observe"` 的 ContextRequest 组装提示，其中：
- 系统 Prompt 使用 `template.identity["observe"]`（Observer 角色描述）
- 注入的能力只包含 `submit_task_assessment`（control capability）
- 消息段包含当前任务描述 + ActStep 的执行 transcript

Observer 调用 LLM，LLM 必须调用 `submit_task_assessment` 工具，ControlCapabilityProvider 将 verdict 写入任务状态，ObserveStep 从中提取出 `Verdict` 对象。

```
Verdict
  taskOutcome:  String    "success" / "failed" / "needs_user_input"
  summary:      String    本轮工作总结（写入 OBSERVER_SUMMARY 类型记忆）
```

#### FinalizeStep

职责：将 ObserveStep 的 Verdict 落盘到记忆，发布 Blackboard，更新 Task 状态。

执行顺序：
1. 若任务有 `outputs`，向 `task.id` 这个 topic 发布 BLACKBOARD_PUBLISH（父任务可通过 blackboard 读取子任务结果）
2. ingest `OBSERVER_SUMMARY`（verdict.summary 作为 content，role=assistant）
3. 根据 verdict.taskOutcome 更新 Task 状态（FINISHED/FAILED/PENDING_HITL）
4. emit TaskFinished/TaskFailed

**为什么 FinalizeStep 不触发 Compact**：FinalizeStep 没有"新工作进来"，compact 是为下一轮腾空间，此时检查是无效的浪费。唯一的 Compact 触发点始终是 ReasonStep 入口（新 task 开始时检查是否需要先腾空间）。

#### CompactStep

职责：压缩 Agent 的记忆历史，减少下轮 Prompt 中的历史消息数量。

它使用 purpose=`"compact"` 的 ContextRequest，组装后调用 LLM 生成摘要文本，然后调用 `memoryProvider.applyCompact()`：
- 将摘要写入 COMPACT_SUMMARY 类型的记忆事件
- 将同 scope 内旧记录（排除最近 `keepLast` 条）标记为 `superseded=true`
- 之后 recallRecent 不再返回 superseded 的记录

LLM 失败时降级到机械截断（无摘要头，只保留最近 N 条），保证 Compact 流程不会因 LLM 故障卡死。

完成后 `loopGuard.updateBaseline(0, afterCount)`，使下轮 ReasonStep 重新测量（无基线状态）。

## 7. Prompt 组装流水线

### 7.1 整体结构

```
ContextRequest
  └─► [多个 ContextSource 并行 fetch]
       └─► 合并 ContextBlock 列表
            └─► BudgetStrategy 裁剪（token 预算内）
                 └─► DefaultComposer 拼装
                      └─► AssembledPrompt（system + messages）
```

### 7.2 ContextRequest

```java
ContextRequest
  purpose:             String                    "act" / "observe" / "compact"
  agent:               Agent
  task:                Task
  session:             Session
  scope:               MemoryScope
  boundCapabilities:   List<Capability>          ReasonStep 已绑定的能力列表
  skillName:           String                    任务分配的技能名
  skillInstructions:   String                    技能 body（已加载）
```

`purpose` 字段决定每个 Source 的行为——不同 purpose 使用不同的系统提示片段和不同的能力子集。

### 7.3 各 ContextSource

| Source 类 | 产出 | 写到 system/messages | purpose 相关 |
|-----------|------|---------------------|-------------|
| `IdentitySource` | Agent 人格描述 | system | `template.identity[purpose]` |
| `CapabilitySource` | 工具列表 JSON + 技能说明 | system | 按 purpose 过滤（act/observe 看到不同 capability）|
| `TaskSpecSource` | 当前任务描述 | messages（最终 user 消息）| 无 |
| `RecentMemorySource` | 历史消息 | messages | 从 memory 查 USER_PROMPT/OBSERVER_SUMMARY/COMPACT_SUMMARY |
| `BlackboardSource` | 父子任务结果 | messages | 通过 topic 订阅读取 |
| `SemanticRecallSource` | 语义相关历史 | messages | 不支持时返空 |
| `KnowledgeRetrievalSource` | RAG 检索结果 | messages | 通过 KnowledgeProvider |

### 7.4 Prompt 最终布局

**System Prompt 结构**（`target="system"` 的 block 按优先级拼接）：

```
{identity text}（来自 IdentityFacet[purpose].text）

## Available Skills
（若有分配技能，注入 skill body，截断至 skillInstructionLimit 字符）

## Available Tools  
（工具列表 JSON）
```

**Messages 结构**（`target="messages"` 的 block 按优先级 + 时序排列）：

```
[早期]  长期背景（blackboard long_term_background 类）
[中期]  历史对话（recall_recent 返回的 USER_PROMPT/OBSERVER_SUMMARY/COMPACT_SUMMARY）
[后期]  参考资料（知识检索）
        子任务结果（blackboard parent_child 类）
[末尾]  当前任务请求（TaskSpecSource，role=user）
```

### 7.5 BudgetStrategy

`budgetTokens = max(contextLimit - 4096, contextLimit / 2)`，优先级裁剪顺序（priority 数越大越早裁）：
- knowledge reference（可裁）
- 长期 blackboard（可裁）
- 旧 history（可裁，oldest first）
- capabilities（低频先裁）
- identity / task_spec（priority=0，不可裁）

## 8. 记忆（Memory）系统

### 8.1 两级压缩模型

| 级别 | 执行者 | 时机 | 输入 | 输出 |
|------|--------|------|------|------|
| 第一级：per-task 压缩 | ObserveStep | 每个 Task 结束后 | ActStep 的多轮 LLM + 工具调用 | 一条 OBSERVER_SUMMARY |
| 第二级：累积压缩 | CompactStep | 累积超限时（由 ReasonStep 触发）| 多个 Task 的 summary 积累 | 一条 COMPACT_SUMMARY + 旧记录 superseded |

Observer 是"写日记"（每天一条），Compact 是"整理日记"（快满了才整理）。两者协作确保记忆可控增长。

### 8.2 PostgresMemoryProvider 实现

数据存储在 `memory_records` 表中：

```sql
memory_records (
  id, session_id, task_id, agent_id,
  event_type, role, content, topic,
  sequence BIGINT,      -- 全局递增，用于排序和基线计算
  superseded BOOLEAN,   -- applyCompact 后旧记录标记为 true
  created_at
)
```

关键查询语义：
- `recallRecent`：`WHERE superseded=false AND event_type IN (?) ORDER BY sequence DESC LIMIT ?`（取最新 N 条，返回前再反转为正序）
- `countRecent`：同上但只 COUNT，不加载内容（高效，用于 Compact 触发判断）
- `applyCompact`：先 INSERT 新的 COMPACT_SUMMARY，然后 UPDATE 旧记录 `SET superseded=true WHERE id NOT IN (最近 keepLast 条)`

### 8.3 Blackboard（黑板）机制

子任务完成后，FinalizeStep 将 `task.outputs` 发布到以 `task.id` 为 topic 的黑板事件。父任务重新激活后，ReasonStep 装配 Prompt 时，BlackboardSource 通过 `subscribeTopic` + `recallTopic` 将子任务结果注入到 messages 段。

这实现了父子任务之间的结果传递，不需要共享 memory scope，避免 scope 污染。

## 9. 能力（Capability）体系

### 9.1 内置 Provider

| Provider | 名称 | 能力 ID 前缀 | 注册时机 |
|---------|------|------------|---------|
| `BuiltinToolsCapabilityProvider` | `"builtin"` | `builtin:` | `LoomeJRuntimeConfig`，条件：`loomej.builtin-tools.enabled=true` |
| `LocalSkillCapabilityProvider` | `"local_skill"` | `skill:` | `LoomeJRuntimeConfig`，条件：skills 目录存在 |
| `SpringAiMcpCapabilityProvider` | `"mcp"` | `mcp:` | `LoomeJRuntimeConfig`（始终注册，初始无工具）|
| `ControlCapabilityProvider` | `"control"` | `control:` | `LoomeJRuntime` 构造时自动注册 |
| `SkillExecutorCapabilityProvider` | `"skill_executor"` | `skill:` | `LoomeJRuntime` 构造时自动注册 |
| `RemoteSkillCapabilityProvider` | `"remote_skill_<name>"` | `skill:` | `SkillSourceManager.@PostConstruct` |

### 9.2 ControlCapabilityProvider

ControlCapabilityProvider 是 core 内置的控制工具集，直接持有 `HitlManager` 引用，按 Session 注册和注销（`registerSession` / `deregisterSession`）。

控制工具列表：

| 工具名 | purpose | 功能 |
|--------|---------|------|
| `submit_task` | `"act"` | 派生单个子任务，当前任务进入 SUSPENDED |
| `submit_plan` | `"act"` | 批量派生子任务，当前任务进入 SUSPENDED |
| `submit_task_assessment` | `"observe"` | ObserveStep 用：写入任务 verdict |
| `request_human_input` | `"act"/"observe"` | 触发 HITL 等待 |
| `set_task_result` | `"act"` | 设置任务 outputs |

控制工具与普通工具走相同的 `ToolCapabilityProvider.invoke()` 接口，但通过 `CapabilityEvent.payload["metadata"]["task_suspended"]` 这个标志字段与 ActStep 通信。ActStep 不感知"这是控制工具"，只读 metadata。

### 9.3 RemoteSkillCapabilityProvider 与 _meta 注入

远程 skill MCP server 通过标准 MCP 协议提供以下 5 个工具：

| MCP 工具名 | 入参 | 出参 |
|-----------|------|------|
| `listSkills` | `{}` | JSON Array，每项 `{name, description, version}` |
| `loadSkillMd` | `{skillName}` | Markdown 文本字符串 |
| `getSkillFiles` | `{skillName}` | 换行分隔的文件路径列表 |
| `loadSkillReference` | `{skillName, referencePath}` | 文件内容字符串 |
| `execSkillScript` | `{skillName, scriptPath}` | 脚本执行输出字符串 |

所有工具调用通过 `McpSchema.CallToolRequest(toolName, args, meta)` 的三参数构造器注入 `_meta`：

```json
{
  "_meta": {
    "netcowork/sessionId": "sess_abc",
    "netcowork/agentId":   "agent_xyz",
    "netcowork/taskId":    "task_123"
  }
}
```

服务端依赖 `taskId` 查找当前任务上下文（如该任务对应的项目路径、环境变量等）。不注入 `_meta` 时服务端会返回"未找到对应的任务"错误。

`_meta` 通过 `ProviderContext` 逐层传递：`LoopContext.providerCtx` → `RemoteSkillCapabilityProvider.ctx` → `RemoteSkillMcpConn.callTool(toolName, args, ctx)` → `buildMeta(ctx)` → `CallToolRequest(_meta)`。

### 9.4 能力优先级与去重

ReasonStep 用 `LinkedHashMap<name, Capability>` 聚合所有 Provider 的能力，遍历顺序：

```
builtin → LocalSkill → MCP → Control（自动注入，不参与遍历）
```

后遍历的 Provider 覆盖前者同名能力，因此 MCP 工具可以覆盖同名 builtin 工具——这是有意设计，允许用户用 MCP 版本替换内置工具实现。

Control capability（submit_task 等）不参与 LinkedHashMap 去重，它们通过独立路径注入 Prompt（purpose 过滤）。

## 10. 事件驱动架构

### 10.1 EventBus

`InProcessEventBus`：在内存中同步分发，所有 emit 调用在发起线程上执行（虚拟线程）。订阅者列表用 `CopyOnWriteArrayList` 保证并发安全。

**为什么不用异步分发**：SSE 需要将事件"实时"推出，异步队列会引入不确定延迟。虚拟线程下同步分发没有线程阻塞代价，不需要复杂化设计。

### 10.2 订阅者

| 订阅者 | 注册时机 | 处理内容 |
|--------|---------|---------|
| `EventPersister` | LoomeJRuntimeConfig 构造时 | 持久化所有非流式事件到 core_events 表 |
| `SnapshotWriter` | LoomeJRuntimeConfig 构造时 | SESSION_FINISHED 时写快照 |
| `SessionEntry.onEvent()` | SessionRegistry.createAndStart() 时 | 翻译为 SSE JSON，写入 sseBuffer |

**流式事件不持久化**：`LLMTokenStreamed` 和 `LLMReasoningStreamed` 是高频低价值事件，不写入 core_events（由 EventPersister 过滤）。

## 11. SSE 流与前端协议

### 11.1 SessionEntry（SSE 状态载体）

每个 Session 在 `SessionRegistry` 中对应一个 `SessionEntry`，维护推流所需的全部状态：

```
SessionEntry
  sessionId:          String
  status:             String             当前 Session 状态（随事件更新）
  sseBuffer:          CopyOnWriteArrayList<String>    SSE JSON 字符串缓冲
  sseFinished:        boolean            Session 是否已结束
  streamingTextBuf:   StringBuilder      LLM token 流聚合缓冲（同步访问）
  pendingInvocations: ConcurrentHashMap<invId, Map>   等待结果的工具调用
  tasks:              ConcurrentHashMap<taskId, Map>  任务状态缓存（用于 task_updated）
  inputTokens:        int                累计输入 token
  outputTokens:       int                累计输出 token
  contextTokens:      int                最近一次的 prompt_tokens
  updatedAt:          String
```

### 11.2 SSE 连接机制

`GET /api/v1/sessions/{id}/stream` 返回 `text/event-stream`：

1. 创建 `SseEmitter`，设置 timeout
2. 若 `entry.sseFinished=true`，立即推 `done` 事件并关闭
3. 否则，从 `sseBuffer` 当前末尾开始监听（新消息通知机制，不回放历史）
4. 连接断开时 `SseEmitter` 失效，但 `sseBuffer` 保留，前端重连后继续从断点接收

### 11.3 SseEventTranslator——core 事件到 SSE 的映射

`SseEventTranslator.translate(Event, SessionEntry)` 是一个纯函数映射器，返回 `List<String>`（一个 core 事件可能翻译为多个 SSE 消息）。

**关键映射规则**：

| core Event | SSE type | 说明 |
|-----------|---------|------|
| `LLMTokenStreamed` | `text_delta` + 追加到 streamingTextBuf | token 逐字推送 |
| `LLMResponseFinished` | `token_update` + `reasoning_done`（若有）+ `text_done` | flush streamingTextBuf |
| `CapabilityInvoked` | 无（存入 pendingInvocations）| 等待结果再推 |
| `CapabilityFinished/Failed` | `tool_call`（普通工具）或 `control_tool_call`（control: 前缀）| 配对 pendingInvocations |
| `HitlRequired` | `waiting_input` | entry.status = "PAUSED_HITL" |
| `SessionFinished` | `done` | entry.sseFinished = true |
| `RUN_CANCELED` | `interrupted` + entry.status = "INTERRUPTED" | 注意：用户中断后 Session 状态在 SSE 层面仍显示 INTERRUPTED |
| `TaskCreated` | `task_created` | 初始化 entry.tasks 缓存 |
| `TaskStarted/Suspended/...` | `task_updated` | 更新 entry.tasks 缓存 |

**`RUN_CANCELED` → `INTERRUPTED` 的说明**：

当前 `SseEventTranslator` 对 `RUN_CANCELED` 事件将 `entry.status` 设置为 `"INTERRUPTED"`（代表前端看到的 Session 状态），推送 SSE `interrupted` 消息。这与 Session 对象本身的 `SessionStatus.CANCELED` 是不同层面的表达——前者是前端协议中的 SSE 状态字符串，后者是 core 层的枚举。前端根据 `interrupted` 事件和 `session_update` 消息决定是否显示恢复按钮。

## 12. 崩溃恢复与事件溯源

### 12.1 事件持久化

`EventPersister` 订阅 `EventBus`，将每个事件（除 `LLM_TOKEN_STREAMED`/`LLM_REASONING_STREAMED`）写入 `core_events` 表：

```sql
core_events (
  id, run_id, session_id, task_id, agent_id,
  event_type, sequence, payload JSONB, timestamp, created_at
)
```

### 12.2 快照（RunStateView）

`SnapshotWriter` 在 `SessionFinished` 时将 `RunStateView`（Session + 所有 Task + Agent 的快照）序列化为 JSON，写入 `run_state_snapshots` 表。快照用于加速恢复，避免全量重放事件。

`RunStateView` 包含：
- `sessions: Map<sessionId, SessionView>`
- `tasks: Map<taskId, TaskView>`
- `agents: Map<agentId, AgentView>`

`Reducers.reduceEvents(events)` 将 core_events 序列 reduce 成 `RunStateView`，`Reducers.applyEvents(delta, base)` 将增量事件应用到快照得到最新视图。

### 12.3 崩溃恢复流程

**进程重启时（Shell 层 `@PostConstruct`）**：

1. `SessionRegistry.loadSessionsFromDb()` 查询 sessions 表中 status 为 RUNNING 的记录
2. 将这些 Session 标记为 INTERRUPTED（状态写回 DB）
3. 前端再次访问时显示"会话已中断，可恢复"

**用户点击恢复（`POST /sessions/{id}/resume`）**：

1. `LoomeJRuntime.resumeSession()` 从 DB 加载所有 tasks 记录
2. 重建 Session 对象（复用原 rootAgentId，保证 memory scope 连续）
3. 重建 TaskManager，恢复 DAG 拓扑
4. 已完成任务（FINISHED/FAILED/CANCELED）注册为 completed，不重新执行
5. 未完成任务（PENDING/ACTIVE/RUNNING/SUSPENDED）重新入队
6. SUSPENDED 任务：若所有子任务已完成则立即重新激活，否则等待 `tryResumeParent()`

**`recoverSession()`（事件溯源路径）**：

当 snapshotStore 可用时，从 `run_state_snapshots` 加载最新快照，再从 core_events 加载快照之后的增量事件，`Reducers.applyEvents()` 重建最新 `RunStateView`，转换为 Session/Task 领域对象，然后走与 `resumeSession()` 相同的后续逻辑。

## 13. 关键架构决策 ADR

### ADR-01：虚拟线程而非响应式编程

**问题**：LLM 调用是长时阻塞 IO，同时需要支持数百个并发 Session。

**决定**：每个 Task 用 `Thread.ofVirtual().start()` 运行，允许在 LLM 调用上自由阻塞。

**理由**：响应式编程（WebFlux/Reactor）在 AgentLoop 这种含深层嵌套调用的场景下极大增加代码复杂度（every method becomes Mono/Flux）。Project Loom 使得"每任务一线程"在数十万规模下仍可行，代码保持同步可读风格。

**代价**：如果 LLM 客户端用了 synchronized 原生方法（而非虚拟线程友好的 IO），会发生线程 pin。需确保所有 IO 路径（DB、HTTP）用 NIO 实现。

### ADR-02：协议层与实现分离（core/shell）

**问题**：测试时不想启动数据库；未来可能切换 LLM 提供商。

**决定**：所有外部依赖定义为 `loomej-core/protocols/` 下的 Java 接口，core 不导入任何 Spring/JDBC 依赖。

**理由**：core 的单元测试可以用 In-memory 实现（`InMemoryMemoryProvider` 等）在毫秒内完成，不依赖外部服务。同时 shell 可以替换任意组件（换 MySQL、换 Redis、换其他 LLM SDK）而不影响 core 逻辑。

### ADR-03：同步 EventBus（In-process，同步分发）

**问题**：需要 SSE 实时推送，但 SSE Emitter 调用是阻塞的。

**决定**：`InProcessEventBus` 在 emit 调用方的虚拟线程上同步调用所有订阅者。

**理由**：订阅者（SSE 推送、DB 持久化）本身是 IO 操作，在虚拟线程上调用不会阻塞平台线程，不需要引入消息队列的异步复杂度。同步分发保证了 SSE 消息的顺序性，避免乱序问题。

**代价**：订阅者的耗时直接串联进 emit 调用方的执行路径。若 DB 写入慢（网络抖动），会延迟 ActStep 继续执行。当前认为这是可接受的，因为 DB 写入通常远快于 LLM 调用。

### ADR-04：Compact 唯一触发点在 ReasonStep 入口

**问题**：何时触发记忆压缩（Compact），以及触发后如何安全地将当前任务挂起。

**决定**：Compact 仅在 ReasonStep 入口检查，触发时通过 TaskManager 派生一个 `TaskKind.COMPACT` 子任务，当前任务进入 SUSPENDED。

**理由**：Compact 的本质是"为新工作腾空间"，所以只在新 Task 开始时（ReasonStep）才有意义。ActStep 内超限时不触发：Observer 即将进行第一级压缩（per-task）；FinalizeStep 时无新工作进来，Compact 是浪费。Compact 作为独立子任务的好处是：它走标准的 Task 生命周期，失败时可以重试，且不打断父任务的 Step 链（父任务直接挂起，Compact 子任务独立运行完后再恢复父任务）。

### ADR-05：_meta 通过 ProviderContext 传递

**问题**：远程 MCP skill server 需要知道当前的 sessionId/agentId/taskId，但 MCP 协议的 tool call 参数只有 `name` 和 `arguments`。

**决定**：通过 `McpSchema.CallToolRequest(toolName, args, meta)` 三参数构造器注入 `_meta`，meta 通过 `ProviderContext` 从 LoopContext 一路传递到 `RemoteSkillMcpConn.callTool()`。

**理由**：MCP 规范支持通过 `_meta` 字段传递框架级元数据，这是标准用法。将上下文放在 `_meta` 而非 `arguments` 中，避免污染用户定义的工具参数 schema，远程 server 可以从 `_meta` 而非 `arguments` 中读取框架注入的上下文。

### ADR-06：CapabilityProvider 列表用 CopyOnWriteArrayList

**问题**：`SkillSourceManager` 在 `@PostConstruct` 中动态添加远程 skill provider，此时系统可能已经在处理请求。

**决定**：`ProviderRegistry.capabilityProviders` 使用 `CopyOnWriteArrayList`，`skillProviderIndex` 在每次 `runTaskInternal()` 时动态重建。

**理由**：CopyOnWriteArrayList 的 `add()` 是原子操作，读者（`capabilityProviders()` 的调用方）看到一致快照。动态重建 `skillProviderIndex` 保证 `@PostConstruct` 后注册的远程 provider 在下一次任务执行时立即可见，不需要重启服务。
