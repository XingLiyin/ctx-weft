Agent 中心化交互机制

外部交互的对象从 session 改为 agent。session 退为容器，只登记成员与主从关系； agent 自己持有状态并被生命周期管理器控制；TaskManager 维持 task 与队列的唯一权威地位不变。 并行收敛一项：各 step 自维护的 LLM 镜像事件全部删除，统一走 LLM_* 并由 gateway 标注调用方。 本页是变更后机制的完整参考：组件职责、状态机、外部 API、以及全部事件的发射点与 payload。

变更摘要

四处职责搬迁。数据层地基已部分具备 agent 粒度，改造集中在状态归属与外部入口。

SessionManager

变更前
会话运行状态机，持有 status，订阅 TaskManager 四条队列聚合信号
变更后
会话内 agent 登记表，持有 agent_ids 集合，订阅 AGENT_INSTANTIATED / AGENT_SPAWNED

AgentRegistry → AgentLifecycleManager

变更前
被动登记表，无状态字段，session/parent 查询靠全表扫
变更后
状态权威：持有 status 与 current_task_id，建 parent→children 索引，发 AGENT_* 事件，提供接收守卫

忙闲状态的归属

变更前
活在 TaskManager 的 _running_agents / busy_agents 里
变更后
TaskManager 保留这两个字段做并发调度；对外可见的忙闲改由 agent 自身的 status 表达

外部输入主通道

变更前
start_session 续跑分支，硬编码打到 root_agent_id
变更后
send_message(agent_id, ...) 显式指定收信 agent，配合 list_agents 发现

已有地基（无需新建）

Agent.parent_agent_id 与 spawn_depth（models.py:263-264）、Task.assigned_agent_id、 PendingHitl 的三级 id（registry.py:51-95）、HitlRequestView.agent_id（hitl.py:141）、 set_agent_llm 都已是 agent 粒度。执行引擎的 TaskManager.drain()（task_manager.py:398-430）本就用 asyncio.create_task 并发调度不同 agent 的 task，上限 _DEFAULT_MAX_CONCURRENT = 4（task_manager.py:52）， 唯一约束是「同一 agent 不并发」。多 agent 真并发是既有能力，本次改造不新建执行机制。

Agent 状态机

五态。终态只由外部显式 cancel 触发，task 走完不会让 agent 终结。

TaskManager 事件 → 状态转移

全部复用既有事件，无需为状态机新增 TASK_* 类型。

消费的事件转移说明
TASK_STARTED→ running开始占用执行
TASK_AWAITING_HUMANrunning → waiting_human触发 ask_user，可接收 HITL 回复
TASK_HUMAN_RESOLVEDwaiting_human → running人工已答复，恢复执行
TASK_INTERRUPTED→ interruptedpause_agent 的底层机制
TASK_RESUMEDinterrupted → runningresume_agent 的底层机制
TASK_REQUEUED→ idle重新排队，暂不占用执行
TASK_SUSPENDED→ idle挂起等子任务（suspended_on_children），此时仍可接外部消息
TASK_FINISHED→ idletask 终态 不是 agent 终态；agent 回到 idle 等下一条消息
TASK_FAILED→ idle
TASK_CANCELED→ idle
TASK_FINALIZED→ idle

三条关键性质

  • idle ≠ 没有活着的 task。 agent 的 task 是跨多轮持续存在的容器；只要 task 未到终态，idle 就是「当前轮次做完了，等下一个输入」，不管输入是用户消息还是子任务完成结果。
  • agent 也是跨多轮的容器。 task 到终态后 agent 依然回到 idle，可接新消息并开启新 task。真正的终态 terminated 仅由外部显式 cancel_agent 触发。
  • 两类输入不对称。 用户消息在 running 时直接报错拒绝、不排队；子任务完成结果永远排队（它不是外部发起的，无法要求重试），等 agent 回到 idle 时自动注入。

AgentSummary 字段

agent_id · parent_agent_id · status · current_task_id · spawn_depth · created_at

发现新 agent 的两条通路

拉取：list_agents 用于首次进入或断线重连后取现状。 推送：既有的 AGENT_INSTANTIATED / AGENT_SPAWNED 本身已带 session_id 与 parent_agent_id， 经既有事件流 / SSE 订阅即可实时感知，无需新增「agent 加入 session」事件；状态变化则由新的 5 种 AGENT_* 事件推送。

待确认

非架构性问题，不阻塞设计评审，留给实现阶段处理。

  • 异步 bus 下 ALM 的状态是最终一致的。EventBus 由 host 实现，同步 drain 只是内置 InProcessEventBus 的特性。若 host 换用异步 / 远程 bus（如 Redis Streams），ALM 的 status 更新相对 TaskManager 的内存态转移存在延迟，assert_can_receive 可能读到陈旧状态而放行本该拒绝的消息。需确认该守卫是否需要额外的同步保证 —— HitlService 已有先例：它刻意不靠订阅驱动续跑，而用 reply_to_hitl 返回值里的 claimed 分流，正是为了避开这类背压问题。
  • TASK_RESUMED 的发射点与 payload。调查中未定位到显式的 payload 构造点，消费方按类型判断。实现 resume_agent 前需核实其实际发射位置与字段。
  • 三条队列事件的去向。TASK_QUEUE_BLOCKED / INTERRUPTED / DRAINED 原本是 SessionManager 唯一的输入。SM 不再消费后，建议保留发射作为外部可观测信号，但需确认没有其他消费者依赖它们。
  • reducers._apply 需扩展。加入 5 种 AGENT_* 的折叠分支，使 rebuild_view 冷重建出的视图与运行时内存态保持一致。被移除的 11 种类型不能直接删分支——旧事件日志重放要保留读取兼容，与 legacy HITL 6 种事件同样的处理方式。
  • host 侧的渲染分流要改。依赖 BACKGROUND_OBSERVE_* 或 RECOGNIZE_INTENT_LLM_PROMPT 判断「这条要不要渲染 / 渲染到哪个面板」的消费方，需改为按 LLM_* 的 caller 字段分流。ReactEventTypes 的 docstring 原话就是「core 只发类型，由 host 决定前端是否渲染」，所以这类消费方大概率存在。
  • RECOGNIZE_INTENT_COMPLETED 的 usage 字段成为冗余。该 step 开始发 LLM_RESPONSE_FINISHED 后，后者已带 usage。可选清理，本设计不强制。
  • 新 AGENT_* 的 payload 是本设计新定义。目录中这 5 条的字段来自本设计而非现有代码，实现时可按需调整。
  • ALM 内部索引的分片策略。parent → children 与 current_task_id 在多 session 下用分 session 分片还是全局字典 + session 过滤，按现有 AgentRegistry 的既有模式决定即可。
  • 测试改动范围。test_runtime_hitl_wiring.py、test_runtime_pause_wiring.py、test_runtime_public_api.py 等依赖 session 状态字段的用例需改读 AgentSummary.status，具体范围留给实现计划梳理。
